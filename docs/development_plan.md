# План разработки прототипа

Документ описывает, что в практической части уже есть, что нужно довести до дипломного состояния и какие задачи связаны с исследованием.

## Текущий статус

Основа прототипа уже реализована:

- Gradio UI для загрузки аудио, видео и текста;
- ASR-воркер на GigaAM;
- LLM-воркер через Ollama;
- методы суммаризации `Map-Reduce`, `Hierarchical`, `Semantic-Cluster`;
- локальная база знаний в JSON;
- ChromaDB + `multilingual-e5-small` для семантического поиска;
- чат по сохраненным лекциям;
- мониторинг воркеров, очередей, GPU и Ollama;
- начальная папка `benchmark/` для оценки ASR, суммаризации и RAG.

Текущие ограничения:

- `Sequential`, `Coarse-to-Fine` и `STA` в коде не являются полноценными методами, а сведены к `Hierarchical` или скрыты из UI;
- `BENCHMARK_REPORT.md` содержит нулевые/черновые результаты и не подходит как финальный эксперимент;
- нет полноценного extractive/MMR baseline;
- нет Evidence-Hierarchical;
- нет финального корпуса лекций и разметки;
- метрики суммаризации пока грубые и должны быть дополнены source-grounded оценкой;
- `FFMPEG_PATH` по умолчанию завязан на локальный Windows-путь.

## Целевое состояние к защите

К защите прототип должен демонстрировать полный pipeline:

1. Пользователь загружает аудио, видео или текст.
2. Система получает транскрипт.
3. Пользователь выбирает метод суммаризации.
4. Система формирует конспект и темы.
5. Материал сохраняется в базу знаний.
6. Запись индексируется для семантического поиска.
7. Пользователь задает вопросы по базе лекций.
8. Экспериментальные скрипты позволяют воспроизвести сравнение методов.

## Этап 1. Стабилизация продукта

Задачи:

- проверить запуск `gateway/app.py` на чистом окружении;
- описать установку и запуск без привязки к старой машине;
- вынести `FFMPEG_PATH` из хардкода в нормальную инструкцию через переменную окружения;
- убедиться, что обработка текстового ввода работает без ASR;
- проверить, что база знаний и RAG-индекс восстанавливаются после перезапуска;
- привести `README.md` к фактическому состоянию после завершения основной разработки.

Критерий готовности: можно показать работающий локальный сценарий на одной лекции.

## Этап 2. Методы суммаризации

Обязательные задачи:

- реализовать Extractive/MMR baseline без LLM-генерации;
- сохранить текущие Map-Reduce и Hierarchical как baseline-методы;
- проверить Semantic-Cluster на реальных лекциях и зафиксировать fallback-логику;
- реализовать MMR-Compress + LLM как гибридный метод предварительного сокращения контекста;
- реализовать Evidence-Hierarchical: при merge передавать не только summary-группы, но и релевантные исходные фрагменты;
- сохранять метаданные: метод, число чанков, число LLM-вызовов, время, длину результата.

Опциональные задачи:

- полноценный Sequential/Refine;
- Coarse-to-Fine: сначала общий outline, затем детальный конспект по разделам;
- настройка размера чанка и overlap через UI.

Критерий готовности: каждый обязательный метод можно запустить на одном и том же транскрипте и получить сохраненный результат.

## Этап 3. Корпус и разметка

Задачи:

- подготовить `data/eval/catalog.json`;
- собрать 6-9 лекций;
- для каждой лекции сохранить транскрипт в едином формате;
- подготовить разметку по формату из `docs/evaluation_protocol.md`;
- отделить материалы для разработки от материалов финального эксперимента.

Критерий готовности: есть воспроизводимый набор входов и аннотаций, на котором можно запускать все методы.

## Этап 4. Экспериментальная инфраструктура

Задачи:

- обновить `benchmark/compare_methods.py`, чтобы он сравнивал актуальный список методов;
- добавить сохранение результатов каждого метода в отдельные файлы;
- добавить расчет `llm_calls`, `time_sec`, `summary_words`, `compression_ratio`;
- добавить таблицу source-grounded оценок из ручной разметки;
- добавить шаблон для экспертной рубрики;
- генерировать финальный отчет только из реальных результатов.

Критерий готовности: одна команда прогоняет корпус и создает таблицы, которые можно вставлять в диплом.

## Этап 5. Финальная демонстрация

Задачи:

- подготовить 1-2 короткие лекции для live/demo сценария;
- проверить работу без интернет-зависимостей, кроме заранее скачанных моделей;
- сделать экспорт конспекта в Markdown;
- подготовить скриншоты интерфейса;
- зафиксировать ограничения и известные сбои.

Критерий готовности: прототип можно показать как локальный продукт, а не только как набор скриптов.

## Что не делать до базовой готовности

- не тратить время на упаковку в desktop-приложение до завершения экспериментов;
- не добавлять много моделей до появления корпуса и оценки;
- не писать финальные выводы до реальных прогонов;
- не расширять UI ради красоты, если pipeline и benchmark еще нестабильны.
