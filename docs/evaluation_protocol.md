# Протокол оценки качества

Этот документ описывает, как честно оценивать методы суммаризации в ВКР. Старые метрики и `BENCHMARK_REPORT.md` можно использовать как инфраструктурный черновик, но не как финальное доказательство качества.

## Почему нельзя ограничиться ROUGE

Учебный конспект не имеет одного правильного эталона. Хороший конспект может менять порядок лекции, группировать фрагменты по темам, переформулировать устную речь и добавлять заголовки. Поэтому overlap-метрики вроде ROUGE и простое совпадение с одним эталоном плохо отражают качество результата.

Для этой задачи нужна многокритериальная оценка:

- сохранены ли темы, понятия, определения и примеры;
- подтверждаются ли утверждения исходным транскриптом;
- можно ли по конспекту ответить на контрольные вопросы;
- получился ли читаемый учебный материал;
- сколько ресурсов потребовал метод.

## Единица эксперимента

Одна единица эксперимента:

- одна лекция;
- один входной транскрипт;
- один метод суммаризации;
- один сгенерированный конспект;
- метаданные запуска и оценки.

Все методы должны получать одинаковый входной транскрипт. Если сравнивается влияние ASR-ошибок, это оформляется отдельным экспериментом: "чистые субтитры" против "ASR-транскрипт".

## Формат разметки

Рекомендуемый формат файла разметки:

```json
{
  "lecture_id": "L001",
  "title": "Название лекции",
  "domain": "physics",
  "source_type": "youtube_subtitles",
  "length_bucket": "medium",
  "topics": [
    {"id": "t1", "name": "Основная тема", "evidence": ["00:01:20-00:05:10"]}
  ],
  "concepts": [
    {"id": "c1", "name": "Термин", "expected_explanation": "Что должно быть раскрыто"}
  ],
  "definitions": [
    {"id": "d1", "term": "Понятие", "evidence_text": "Фрагмент источника"}
  ],
  "examples": [
    {"id": "e1", "name": "Пример", "evidence_text": "Фрагмент источника"}
  ],
  "questions": [
    {
      "id": "q1",
      "question": "Контрольный вопрос?",
      "expected_answer": "Краткий ожидаемый ответ",
      "evidence": ["00:10:00-00:11:30"]
    }
  ]
}
```

Для минимальной версии достаточно заполнить темы, понятия, определения, примеры и 5 контрольных вопросов на лекцию.

## Автоматические метрики

Эти метрики считаются для всех запусков и помогают быстро увидеть аномалии:

| Метрика | Что показывает | Ограничение |
| --- | --- | --- |
| `compression_ratio` | насколько сильно сжат текст | не измеряет качество |
| `summary_words` | длина результата | не измеряет полноту |
| `term_coverage` | грубое покрытие слов/терминов | путает частые слова с понятиями |
| `faithfulness` по n-граммам | лексическая близость к источнику | наказывает нормальный парафраз |
| `redundancy` | повторы в конспекте | требует реализации |
| `llm_calls` | число вызовов LLM | важно для стоимости |
| `time_sec` | время обработки | зависит от машины |
| `peak_vram` | пиковая VRAM | желательно фиксировать хотя бы через `nvidia-smi` |

Автоматические метрики первого слоя не должны быть единственным основанием для вывода о качестве.

## Source-grounded оценка

Главная оценка качества делается по разметке лекции.

Шкала покрытия для каждого элемента:

- `1`: элемент сохранен корректно;
- `0.5`: элемент упомянут, но неполно или с незначительной потерей;
- `0`: элемент отсутствует или искажен.

Считаемые показатели:

- `topic_coverage`: средняя оценка по темам;
- `concept_coverage`: средняя оценка по понятиям;
- `definition_coverage`: средняя оценка по определениям;
- `example_coverage`: средняя оценка по примерам;
- `qa_answerability`: доля вопросов, на которые в конспекте есть ответ;
- `qa_correctness`: доля вопросов, на которые ответ корректен;
- `claim_support_rate`: доля проверенных утверждений конспекта, подтвержденных транскриптом;
- `unsupported_claims`: число неподтвержденных утверждений.

Для claim support достаточно вручную проверить 10-20 ключевых утверждений на метод в минимальной версии исследования.

## Экспертная рубрика

Каждый конспект оценивается по шкале 1-5:

| Критерий | Вопрос |
| --- | --- |
| Полнота | Сохранены ли основные темы лекции? |
| Фактическая точность | Нет ли искажений и неподтвержденных утверждений? |
| Понятия и определения | Объяснены ли ключевые термины? |
| Примеры | Сохранены ли важные примеры и кейсы? |
| Структура | Похож ли результат на учебный конспект? |
| Читаемость | Можно ли использовать текст для повторения? |
| Компактность | Нет ли лишней воды и повторов? |

Даже один эксперт допустим, если правила оценки фиксированы заранее и одинаковы для всех методов. В тексте диплома это нужно честно назвать экспертной оценкой по фиксированной рубрике.

## Стоимость метода

Для локальной системы качество нельзя отделять от стоимости. Для каждого запуска фиксируются:

- модель LLM;
- размер контекста;
- число чанков;
- число LLM-вызовов;
- время обработки;
- ошибки или fallback на CPU;
- пиковая VRAM, если измеряется;
- размер входа и выхода в словах.

Метод, который немного выигрывает по качеству, но работает в несколько раз дольше или нестабилен на 4 GB VRAM, может быть хуже для практического прототипа.

## Минимальный план эксперимента

1. Подготовить 6 лекций.
2. Для каждой лекции заполнить разметку.
3. Прогнать 5 методов: Extractive/MMR, Map-Reduce, Hierarchical, Semantic-Cluster, Evidence-Hierarchical.
4. Для каждого результата посчитать автоматические метрики.
5. Вручную оценить покрытие тем, понятий, определений, примеров и QA.
6. Проверить 10-20 утверждений на фактическую опору.
7. Заполнить экспертную рубрику.
8. Построить таблицы средних значений по методам.
9. Разобрать 2-3 характерных ошибки каждого метода.
10. Сформулировать вывод о применимости методов для локального прототипа.

## Правила честности

- Не использовать нулевые или тестовые benchmark-таблицы как экспериментальный результат.
- Не писать, что метод реализован, если в коде он является alias/fallback на другой метод.
- Не сравнивать методы на разных входах.
- Не делать вывод о качестве только по одному примеру.
- Не выдавать YouTube-субтитры за ASR-результат, если они не были получены через ASR-воркер.
- Не скрывать ограничения: малый корпус, ручная разметка, зависимость от локальной LLM, ошибки ASR и субъективность экспертной оценки.
