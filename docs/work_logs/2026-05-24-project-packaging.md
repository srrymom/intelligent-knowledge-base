# Упрощение упаковки и запуска проекта

Дата: 2026-05-24
Статус: `partial`

## Коротко

Разбиралась задача упаковки проекта: сейчас для запуска нужно вручную ставить несколько окружений, внешние сервисы и модели, из-за чего проект сложно развернуть на новой машине.

## Ход работы

### Проблема

Текущий запуск проекта требует слишком много ручных действий:

- создать основное окружение `gradio-env`;
- создать ASR-окружение `asr/.venv`;
- создать LLM-окружение `llm/.venv`;
- установить системный `ffmpeg`;
- установить и запустить Ollama;
- скачать модель `qwen2.5:3b`;
- поставить зависимости для ChromaDB, Sentence Transformers, GigaAM, PyTorch и TorchCodec;
- настроить переменные окружения при необходимости.

Из-за этого проект трудно показать, трудно перенести на другую машину и трудно использовать как нормальный локальный прототип.

### Сделано

Проверена текущая структура запуска по `docs/setup_run_guide.md` и зависимостям:

- `requirements.txt` отвечает за UI, RAG и базу знаний;
- `asr/requirements.txt` отвечает за GigaAM/ASR;
- `llm/requirements.txt` отвечает за LLM-воркер и методы суммаризации;
- `benchmark/requirements.txt` используется отдельно для оценки.

Вывод: проблема не в одной конкретной зависимости, а в том, что проект состоит из нескольких тяжелых частей, которые сейчас пользователь должен собирать вручную.

### Проблема

Возник вопрос, можно ли упаковать проект как одно приложение или `.exe`.

### Сделано

Рассмотрен вариант PyInstaller/единый `.exe`.

Решение: не выбирать этот вариант как основной.

Причины:

- PyTorch, GigaAM, TorchCodec и Sentence Transformers плохо подходят для простой упаковки в `.exe`;
- Ollama все равно остается отдельным сервисом;
- LLM-модель нецелесообразно вшивать в исполняемый файл;
- итоговый размер будет очень большим;
- отладка упаковки может занять больше времени, чем стабилизация самого прототипа.

### Проблема

Рассматривался вариант Docker/Docker Compose.

### Сделано

Docker признан возможным, но не оптимальным первым шагом.

Плюсы:

- воспроизводимость окружения;
- можно запускать одной командой;
- удобно для Linux/WSL.

Минусы:

- GPU/CUDA внутри Docker требует отдельной настройки;
- Ollama нужно либо запускать внутри контейнера, либо подключать снаружи;
- образ с PyTorch, GigaAM и ffmpeg будет тяжелым;
- для Windows это может оказаться сложнее текущего запуска.

Вывод: Docker можно оставить как перспективу, но не делать главным способом упаковки на ближайшем этапе.

### Проблема

Нужно выбрать реалистичный способ упростить запуск без полной перестройки архитектуры.

### Сделано

Выбран основной подход: scripted deployment.

Идея:

- добавить скрипты установки;
- добавить скрипты запуска;
- добавить скрипт диагностики окружения;
- добавить `.env.example`;
- разделить запуск на режимы.

Предлагаемая структура:

```text
scripts/
  install.sh
  install.ps1
  run.sh
  run.ps1
  doctor.py
.env.example
docs/deployment.md
```

### Проблема

Полный проект тяжелый из-за ASR, но часть функционала может работать без ASR.

### Сделано

Предложено разделить установку и запуск на режимы:

- `lite` - обработка готового текста, суммаризация, база знаний, экспорт;
- `full` - полный pipeline с аудио/видео и ASR;
- `research` - benchmark-скрипты и сравнение методов.

Это позволит запускать минимально рабочий вариант даже на машине, где ASR еще не настроен.

## Итог

Для текущего состояния проекта наиболее подходящий способ упаковки - не `.exe` и не Docker как первый шаг, а набор скриптов установки, запуска и диагностики окружения.

Главная идея: скрыть сложность трех Python-окружений, Ollama, ffmpeg и моделей за командами `install`, `run` и `doctor`, а также добавить режимы `lite`, `full` и `research`.

## Осталось

- Создать `scripts/install.sh` и `scripts/install.ps1`.
- Создать `scripts/run.sh` и `scripts/run.ps1`.
- Добавить `.env.example`.
- Написать `docs/deployment.md`.
- При необходимости доработать запуск приложения, чтобы режим `lite` мог работать без ASR-окружения.

## Для отчета

- Проект имеет сложную структуру развертывания из-за использования нескольких локальных компонентов: Gradio-интерфейса, ASR-воркера GigaAM, LLM-воркера Ollama и RAG-модуля ChromaDB.
- В качестве основного способа упрощения развертывания выбран подход scripted deployment: скрипты установки, запуска и диагностики окружения.
- Полная упаковка в единый `.exe` признана нецелесообразной из-за тяжелых зависимостей PyTorch/GigaAM, внешнего сервиса Ollama и локальных языковых моделей.
- Для повышения удобства предлагается разделить систему на режимы запуска: `lite`, `full` и `research`.
- Такой подход позволяет быстро запускать базовый функционал обработки текста и отдельно подключать тяжелые компоненты ASR и экспериментальной оценки.
