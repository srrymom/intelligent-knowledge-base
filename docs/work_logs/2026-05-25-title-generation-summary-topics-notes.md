Была проблема: после закрытия gateway оставались живые ASR/LLM воркеры, из-за этого мог продолжать работать старый код воркера.

Сделали: проверили точки запуска и жизненный цикл процессов в gateway (`runtime.py`, `app.py`, `monitor.py`), подтвердили что явного shutdown при выходе не было.

Возникла проблема: монитор воркеров мог перезапускать процессы даже в момент штатного завершения gateway.

Сделали: добавили в `gateway/monitor.py` флаг `_shutdown_in_progress`, чтобы в фазе остановки не запускался autorestart.

Сделали: добавили `shutdown_workers()` в `gateway/monitor.py`:
- собирает PID из зарегистрированного `Popen` и singleton pid-файла,
- завершает дерево процессов через `psutil` (`terminate` -> `kill` fallback),
- снимает GPU owner/request,
- зануляет `proc` в реестре воркеров,
- пишет DIAG-события начала/конца shutdown.

Сделали: подключили shutdown в `gateway/app.py` через `finally` после `launch_ui()`, чтобы остановка срабатывала и при обычном выходе, и при исключении.

Сделали: поправили путь python для Windows при перезапуске воркера в `monitor.py` (`python.exe` вместо `python`).

Проверили: `python -m py_compile gateway/app.py gateway/monitor.py gateway/runtime.py` — ошибок нет.

Проверили: вручную остановили текущие зависшие процессы по PID (ASR 7428, LLM 27248), затем убедились, что процессы больше не живы.

Итог: теперь при закрытии gateway воркеры завершаются штатно и не остаются висеть со старым кодом в памяти.

Для отчета:
- Реализован явный lifecycle shutdown ASR/LLM воркеров.
- Убран конфликт shutdown vs autorestart в мониторинге.
- Подтверждена компиляционная и операционная проверка фикса.
