# Защита от дублей ASR/LLM-воркеров и гонок очереди

Была проблема: при загрузке медиа один и тот же файл мог одновременно подхватываться двумя ASR-воркерами. В логах это проявлялось как две строки `Транскрибирую` / `DIAG WORKER_CLAIM` для одного uuid с разными pid. Из-за этого один процесс удалял файл из `data/queue`, второй падал с `FileNotFoundError` или `Failed to load audio`, а LLM мог начать суммаризацию по неполному или ошибочному transcript.

Сделали:

- добавили диагностические строки `DIAG` в `asr/worker.py`, `llm/worker.py`, `gateway/runtime.py`, `gateway/monitor.py`;
- начали логировать `pid`, `ppid`, `sys.executable`, `argv`, регистрацию воркеров, перезапуски монитором и факт захвата конкретного uuid;
- воспроизвели проблему на реальном запуске: один uuid `035dd5fc-8d5a-4b99-a4dc-78dd1ca758ac` одновременно взяли ASR-процессы `pid=17204` и `pid=1056`;
- дополнительно через `Get-CimInstance Win32_Process` подтвердили, что в системе висели старый комплект воркеров и новый комплект от текущего `gateway/app.py`;
- добавили `QUEUE_PROCESSING_DIR = data/queue_processing` в `shared/config.py`;
- изменили ASR-очередь: воркер теперь сначала атомарно забирает файл из `data/queue` в `data/queue_processing` через `os.replace()`, и только после успешного захвата грузит/использует GigaAM для этого файла;
- добавили LLM-защиту от двойной обработки transcript: перед обработкой создается атомарный lock-файл `UUID.json.lock` через `os.O_CREAT | os.O_EXCL`;
- добавили общий модуль `shared/process_singleton.py` с pid-lock guard для одного живого процесса на роль;
- добавили pid-файлы в `shared/config.py`: `gateway.pid`, `asr_worker.pid`, `llm_worker.pid`;
- подключили singleton-защиту к `gateway/app.py`, `asr/worker.py`, `llm/worker.py`;
- теперь второй `gateway/app.py`, второй ASR worker или второй LLM worker должен увидеть живой pid-lock, записать `DIAG SINGLETON_EXISTS` и завершиться до начала работы.

Возникла проблема: уже запущенные до исправления старые процессы не знают про новый singleton-код и могут продолжать висеть в системе.

Сделали: отдельно зафиксировали список текущих старых pid и команду для одноразовой очистки:

```powershell
Stop-Process -Id 13548,25460,1056,10584,15660,11944,24136,16712,23528,6616 -Force
```

После этого приложение нужно запускать заново:

```powershell
python gateway\app.py
```

Проверили:

- `python -m py_compile shared/config.py shared/process_singleton.py gateway/app.py asr/worker.py llm/worker.py gateway/runtime.py gateway/monitor.py`
- ручную проверку singleton-логики: при lock-файле с живым pid новый экземпляр получает `DIAG SINGLETON_EXISTS` и не захватывает роль;
- диагностикой процесса подтвердили исходную причину: одновременно были живы старый и новый комплекты воркеров.

Итог: добавлены два уровня защиты. Первый уровень предотвращает саму ситуацию с несколькими экземплярами gateway/ASR/LLM через pid-lock singleton. Второй уровень защищает данные, если старый или внешний процесс все же остался жив: ASR атомарно переносит файл в `queue_processing`, а LLM атомарно блокирует transcript перед обработкой.

Что осталось:

- один раз остановить старые процессы, запущенные до внедрения singleton;
- после чистого перезапуска проверить в `data/activity.log`, что для одного uuid появляется только один `DIAG CLAIM_OK` и один `DIAG WORKER_CLAIM`;
- после подтверждения можно убрать часть временных `DIAG`-логов или оставить их до стабилизации прототипа.

Для отчета:

Устранена критическая гонка в конвейере обработки медиа: добавлены диагностические логи, атомарный захват заданий ASR/LLM и singleton-защита процессов. Это предотвращает одновременную обработку одного файла несколькими воркерами, снижает риск повреждения транскрипции и делает запуск системы устойчивее при повторном старте приложения.
