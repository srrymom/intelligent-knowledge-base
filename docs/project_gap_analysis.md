# Gap-анализ: старое описание, спринт и текущий код

Документ фиксирует расхождения между тремя состояниями проекта:

- курсовая работа из `.workbench/Варков_Курсовая_работа_исправленная (3).txt`;
- отчёт спринта из `.workbench/Варков Спринт 1.docx`;
- фактическая реализация в репозитории.

Главный вывод: текущий код в целом соответствует практической части курсовой, но исследовательская часть из спринта реализована только частично. Для диплома нужно либо расширить код под выбранную исследовательскую постановку, либо честно сузить описание методов.

## Что описано в курсовой

Курсовая описывает локальную систему обработки аудиолекций:

- загрузка аудио, видео или готового текста;
- автоматическая транскрипция русской речи;
- суммаризация транскрипта;
- сохранение результата в локальной базе знаний;
- семантический поиск;
- ответы на вопросы по материалам лекции через RAG;
- мониторинг, логирование и последовательное использование GPU.

Практическая архитектура из курсовой в целом совпадает с текущим репозиторием: `gateway`, `asr`, `llm`, `rag`, `storage`, `shared`, файловые очереди и локальная база знаний действительно существуют.

При этом в курсовой исследовательское ядро местами сформулировано уже устаревшим образом: как сравнение прямой и иерархической суммаризации. Это слабее и уже не совпадает со спринтом, где выбран более широкий набор методов.

## Что добавляет спринт

Спринт переводит исследование из продуктового описания в сравнение методов суммаризации длинных лекционных ASR-транскриптов.

В спринте выбран набор методов для дальнейшего сравнения:

- `Map-Reduce`;
- `Hierarchical`;
- `Semantic-Cluster`;
- `Extractive-Rank` или TextRank-like baseline;
- `MMR-Compress + LLM`;
- `Evidence-Hierarchical`.

Также в спринте прямо указаны будущие работы:

- добавить экстрактивный отбор фрагментов;
- реализовать MMR-отбор важных и неповторяющихся частей;
- реализовать гибридный `MMR-Compress + LLM`;
- реализовать `Evidence-Hierarchical`;
- подготовить тестовые транскрипты;
- фиксировать время обработки, длину результата, коэффициент сжатия и оценку полноты.

Это важнее для диплома, чем старое утверждение курсовой про сравнение только прямой и иерархической суммаризации.

## Что реально есть в коде

| Область | Описано | Реализовано | Расхождение |
| --- | --- | --- | --- |
| UI | Загрузка аудио, видео, текста | В UI есть вкладки аудио, видео, текст | Видео загружается, но ASR-воркер не берёт `.mp4/.mkv/.avi/.mov` из очереди |
| ASR | Русская транскрипция через GigaAM | Есть `asr/worker.py`, GigaAM, сегменты с таймкодами | Нет полноценной обработки видеофайлов на уровне очереди ASR |
| Суммаризация | Несколько методов обработки длинного текста | Есть `Map-Reduce`, `Hierarchical`, `Semantic-Cluster` | Нет `Extractive-Rank`, `MMR-Compress`, `Evidence-Hierarchical` |
| Map-Reduce | Независимый map и финальный reduce | Есть flat merge | Для длинных лекций при `>4` чанках автоматически превращается в `Hierarchical`, поэтому это не чистый Map-Reduce |
| Hierarchical | Древовидное слияние | Реализовано | Соответствует описанию |
| Semantic-Cluster | Кластеризация смысловых фрагментов | Реализован KMeans по summary-чанкам | Требует проверки на реальном корпусе; при отсутствии зависимостей fallback на `Hierarchical` |
| Sequential/Refine | Дополнительный метод | Есть функция `_sequential_merge` | Метод скрыт из UI и нормализуется в `Hierarchical`, то есть как отдельный метод фактически не доступен |
| Coarse-to-Fine/STA | Возможные методы | Есть заглушки | Не реализованы как самостоятельные методы |
| RAG | Ответы с опорой на фрагменты | Есть ChromaDB + top-5 chunks + Ollama | В интерфейсе источники показываются как записи/лекции, а не конкретные найденные фрагменты с таймкодами |
| База знаний | Хранение транскрипта, конспекта, тем | Реализовано JSON-файлами | Векторные представления не хранятся в JSON, а отдельно в ChromaDB; это нормально, но в тексте надо описывать точно |
| Мониторинг GPU | Последовательное использование моделей | Реализован файловый `gpu_state.json`, lock и выгрузка моделей | Соответствует идее, но это прототипный механизм, а не полноценный scheduler |
| Benchmark | Оценка ASR, summary, RAG | Есть скрипты | Старый `BENCHMARK_REPORT.md` содержит нулевые/черновые результаты и не доказывает качество |

## Главные несоответствия для диплома

### 1. Видео заявлено, но pipeline неполный

В UI есть вкладка "Видео", а курсовая говорит об аудио- и видеоматериалах. Однако `asr/worker.py` обрабатывает только аудио-расширения:

```text
.wav, .mp3, .ogg, .flac, .m4a, .aac
```

Если в очередь попадает `.mp4`, ASR-воркер его не подхватит. Нужно либо добавить извлечение аудио из видео, либо в дипломе временно честно ограничить практический сценарий аудио и текстом.

### 2. Исследовательские методы из спринта не реализованы полностью

Спринт требует сравнить шесть методов, но в UI и `SUMMARIZATION_METHODS` доступны только:

```text
Map-Reduce
Hierarchical
Semantic-Cluster
```

Для дипломной исследовательской части ещё нужны минимум:

- `Extractive-Rank` или `MMR` baseline;
- `MMR-Compress + LLM`;
- `Evidence-Hierarchical`.

Без них исследование будет заметно слабее, чем заявлено в спринте.

### 3. Некоторые методы в коде являются заглушками

`Sequential`, `Coarse-to-Fine` и `STA` встречаются в коде, но не должны описываться как реализованные методы сравнения:

- `Sequential` нормализуется в `Hierarchical`, если приходит через публичный API;
- `Coarse-to-Fine` сводится к `_hierarchical_merge`;
- `STA` сводится к `_hierarchical_merge`.

Их можно оставить в обзоре литературы или планах, но не в таблице экспериментальных результатов.

### 4. Старый benchmark нельзя использовать как результат

`BENCHMARK_REPORT.md` содержит нули и строки "нет данных". Это можно использовать только как след инфраструктуры, но не как эксперимент. Для диплома нужны новые прогоны на корпусе и разметке.

### 5. RAG-источники в UI менее точные, чем описано

Код RAG ищет top-5 текстовых чанков, но UI показывает пользователю в основном названия найденных записей. Для диплома лучше либо доработать вывод конкретных фрагментов, либо формулировать мягче: "ответ сопровождается найденными записями/источниками", а не "каждое утверждение сопровождается фрагментом и таймкодом".

### 6. Формулировка исследовательского ядра изменилась

Курсовая местами говорит о сравнении прямой и иерархической суммаризации. Спринт уже говорит о сравнении разных классов методов. Для диплома лучше принять новую формулировку:

> сравнение методов суммаризации длинных русскоязычных ASR-транскриптов лекций в условиях локальной малой LLM и ограниченной VRAM.

Прямую суммаризацию можно оставить только как теоретический baseline для коротких текстов, но не как центральный метод для длинных лекций.

## Что нужно поправить в документации

1. В курсовую/дипломную главу с требованиями добавить честную оговорку: видео поддерживается после извлечения аудиодорожки, если эта функция будет реализована.
2. Убрать или переписать утверждение, что эксперимент уже проведён.
3. Развести "реализовано сейчас" и "планируется для исследования".
4. В таблице методов отметить, что `Sequential`, `Coarse-to-Fine`, `STA` пока не являются самостоятельными реализациями.
5. В README после доработок указать фактический список методов.
6. Для benchmark-документов явно написать, что старые нулевые отчёты не являются результатами ВКР.

## Что нужно поправить в коде

P0 для соответствия спринту и дипломной постановке:

- добавить обработку видео или убрать видео из заявленного обязательного сценария;
- реализовать `Extractive-Rank/MMR` baseline;
- реализовать `MMR-Compress + LLM`;
- реализовать `Evidence-Hierarchical`;
- обновить `benchmark/compare_methods.py` под актуальный список методов;
- сохранять метаданные эксперимента: метод, число чанков, число LLM-вызовов, время, длина входа и выхода;
- подготовить корпус и разметку по `docs/evaluation_protocol.md`.

P1 после этого:

- вывести в RAG-чате конкретные найденные фрагменты;
- добавить таймкоды источников в ответы;
- сделать Semantic-Cluster устойчивее и логировать fallback;
- добавить экспорт экспериментальных результатов в таблицы для диплома.

## Как это влияет на новые документы

Файлы, созданные в `docs/`, в целом выбрали правильное направление: практический прототип плюс исследование методов суммаризации. Но после чтения спринта нужно считать `Extractive/MMR`, `MMR-Compress` и `Evidence-Hierarchical` не просто желательными, а центральными задачами следующего этапа.

Иными словами:

- `docs/diploma_project.md` подходит как новая общая рамка;
- `docs/research_plan.md` нужно читать вместе с этим gap-анализом;
- `docs/development_plan.md` правильно отмечает недостающие методы, но приоритет `MMR-Compress + LLM` нужно поднять до P0;
- `docs/evaluation_protocol.md` остается актуальным, потому что старые автоматические метрики недостаточны.
